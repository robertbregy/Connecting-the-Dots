Behind a click: how the Internet works

You typed a URL. Now follow what actually happens: the browser reads its parts, DNS finds an IP address, networks reach the server, HTTPS protects the connection, and the browser builds the page.

The Internet is a network of networks. Names such as example.com are convenient for people; networks forward data using IP addresses. DNS connects those two worlds. The Web then uses that network to exchange requests, responses and content.

A URL tells the browser how, where and what to ask for

You typed https://www.example.com/news. https:// says how to communicate; www.example.com is the name to reach; /news is the requested resource. Before anything travels, the browser separates those jobs.

REMEMBER THISA URL is not just a website name: it contains different instructions for the browser.
One level deeper

A URL can also contain a port, query parameters and a fragment. We use a deliberately simple address here so the roles are visible without extra syntax.

The browser has to find www.example.com

People use readable names; the network needs to know which IP address should receive the data. The browser therefore relies on a DNS resolver to find where www.example.com can be reached.

REMEMBER THISNames are for people; IP addresses let networks reach destinations.
One level deeper

If a valid answer is already cached on the device or resolver, much of the DNS lookup can be skipped. The resolver may be supplied by your provider, organization or a service you choose.

DNS follows a hierarchy

If the answer is not already cached, the resolver can start at the DNS root. The root points to .com; the .com servers point to the DNS responsible for example.com. The final dot in www.example.com. represents the root and is normally omitted.

REMEMBER THIS.com is not decoration: it is a real level in the DNS hierarchy.
One level deeper

The root and TLD mostly provide delegations: directions about where to ask next. They do not host the web page or carry its content. Running a TLD is a different role from hosting a website.

The name becomes an IP address

The authoritative DNS for example.com returns the requested data. The resolver gives it to your device. In this simulation: www.example.com → 192.0.2.10.

REMEMBER THISDNS does not carry the page: it turns a name into information that helps locate the service.
One level deeper

Authoritative DNS servers publish data for the domains they serve. A records contain IPv4 addresses; AAAA records contain IPv6 addresses. One name can have several addresses, and several names can share an address.

Now the network knows where to send the packets

With the IP address available, packets can cross routers and networks until they reach the server. The Internet is not one network: it is a network of networks exchanging traffic.

REMEMBER THISThe IP identifies the destination; routers decide hop by hop how to reach it.
One level deeper

IP handles addressing and forwarding without guaranteeing delivery on its own. HTTP/1.1 and HTTP/2 normally use TCP; HTTP/3 uses QUIC over UDP. These transport choices sit above IP and help the exchange arrive reliably and efficiently.

The browser creates a protected connection

For HTTPS, the browser checks the certificate presented by the server for the requested name and establishes an encrypted connection. Data can now travel protected between browser and server.

REMEMBER THISHTTPS protects the transport and authenticates the server for that name; it does not guarantee that the content is true or trustworthy.
One level deeper

HTTPS protects communication and authenticates the server for that name. It does not certify that the operator is honest or the content is true. DNSSEC has a different job: verifying the origin and integrity of DNS data.

The browser asks for /news and builds what you see

Over the ready connection, the browser requests /news. The server responds with content and instructions; the browser interprets HTML, CSS, images and JavaScript and assembles the page.

REMEMBER THISThe page is the response to a request: the domain is the name used to reach the service, not the page itself.
One level deeper

A visit may require more files, other servers and additional DNS lookups. A domain name and a website are separate things: you can move the content while keeping the same name and changing DNS.

What is a dot?

A domain is a technical identifier with legal, economic, institutional and cultural dimensions. These eight perspectives explain what can gather around one name.
01

Address

A human-readable identifier that helps users and software find Internet resources.

02

Contract

A registration exists through agreements among registrant, registrar and registry.

03

Market

Names can carry retail prices, premium pricing, renewals and secondary-market value.

04

Jurisdiction

Eligibility, policies and legal duties vary across namespaces and operators.

05

Identity

A domain can accumulate reputation and become a persistent identifier for a person, place or institution.

06

Trust boundary

Verification, DNSSEC and registry rules can add trust signals around a name.

07

Cultural sign

Communities and language can give a TLD meanings that its original designation never anticipated.

08

Political object

Country codes, city names and allocation disputes can reflect institutions, borders and public authority.

The dot is technical. What societies build around it is not.
A useful way to read a TLD is to ask which layer is doing the work: addressing, allocation, governance, trust, market value, identity or cultural meaning.

Who does what?

The Internet has no single “owner”. It works through distinct roles, contracts and technical coordination.
POLICY

ICANN

Coordinates policies and contracts for generic top-level domains through a global multistakeholder model.

ROOT

IANA / PTI

Acts as Root Zone Manager: PTI receives and validates TLD change requests and manages the authoritative delegation data for the DNS root.

MAINTAIN

Root Zone Maintainer

Verisign implements validated root-zone changes as the operational Root Zone Maintainer under contract with ICANN.

GOVERNANCE

Registry operator

Operates a TLD and its authoritative registry database. gTLD operators work under ICANN registry agreements; ccTLD governance arrangements differ.

TECH

Registry Service Provider

Provides critical technical registry services such as DNS and registration infrastructure for the registry operator.

RETAIL

Registrar

For gTLDs, an ICANN-accredited registrar provides the direct registration channel to registrants. ccTLDs use their own registry and registrar models.

USER

Registrant

The person or organization that registers and uses a domain name under the TLD.

How a new TLD is born

The 2026 process is not “apply and receive”. It is a staged public process.
01
Application

Applicant files the application and pays the required fee.

02
Reveal

ICANN publishes public application data and identifies identical-string contention.

03
Input & objections

Community input, formal objections and relevant government advice can enter the process.

04
Evaluation

String, applicant, operational, financial and technical components are evaluated.

05
Contention

If multiple applicants seek the same or confusingly similar string, the contention must be resolved.

06
Contract

A successful applicant signs the Base Registry Agreement with ICANN.

07
Delegation

After onboarding and technical checks, IANA/PTI processes the delegation request and the Root Zone Maintainer implements the validated change in the DNS root.

08
Launch

Only then can the registry move toward actually using and allocating names under the TLD.

Power is a stack, not a dot on a map

Six different ways an application can stop

'Rejected' is too crude. The process contains different gates, and withdrawal is not a rejection.

01

Administrative gate

The application can fail before substantive evaluation: missing fee, incomplete submission or another formal defect.

02

Support eligibility

An applicant seeking financial assistance can be excluded if it does not meet the support-program criteria.

03

Evaluation failure

Financial, operational, geographic or other criteria can prevent an application from advancing, sometimes after Extended Evaluation.

04

Public-policy stop

Consensus GAC advice can create a strong presumption that an application should not be approved, subject to Board consideration.

05

Technical-safety stop

A string can be stopped because delegation itself is considered unsafe, regardless of who applied for it.

06

Withdrawal

The applicant can leave voluntarily. That is an outcome, but it must not be mislabeled as an ICANN rejection.

How a TLD dispute can enter the system

Not every fight is a lawsuit. The new-gTLD process has several formal routes for public-policy concerns, rights claims, community claims, competition and accountability review.

01

GAC advice

Governments can raise public-policy concerns through the Governmental Advisory Committee. Board treatment depends on the form of the advice and the applicable rules.

02

Formal objection

Applications can face String Confusion, Legal Rights, Community or Limited Public Interest objections before independent dispute-resolution providers.

03

Community Priority Evaluation

A qualifying community application in a contention set can seek priority by meeting the Applicant Guidebook criteria.

04

Contention resolution / auction

When identical-string contention remains unresolved, an ICANN auction of last resort can determine which eligible applicant proceeds.

05

Accountability review

Reconsideration and the Independent Review Process test whether ICANN followed its Bylaws, Articles and established procedures.

06

ICANN Board decision

Some disputes ultimately require the Board to weigh application rules, GAC advice, accountability findings and the public interest.

Why apply for a city name at the top level?

A city TLD is not simply another ending for web addresses. It creates a governed namespace directly associated with a place, in which recognition, access and responsibility can be designed deliberately.

Governance

If delegated, the City could define eligibility, allocation and use rules for names under .lugano within the ICANN framework and applicable law.

Stewardship of the name

The namespace would give the City a direct governance role over how the name “Lugano” is used inside .lugano, including proportionate rules against misuse.

Progressive opening

The public project envisages a gradual path: first City-linked services and entities, then potentially businesses, associations, culture, sport, academia and other actors with a concrete territorial link.

What makes a TLD successful?

Registration volume is only one metric. A brand TLD, a verified community namespace and a civic TLD may have completely different purposes, so success has to be measured against mission.

01

Scale

How many names are registered, and how quickly the namespace grows or contracts.

02

Active use

Whether names resolve to real services, websites, email or machine-readable endpoints.

03

Renewal

Whether registrants keep names over time rather than treating the namespace as disposable inventory.

04

Trust and abuse

Security controls, abuse rates, verification requirements and credibility attached to the namespace.

05

Diversity

How registrations are distributed across registrants, registrars, sectors and geographies.

06

Purpose fulfilment

Whether the namespace achieves the mission for which it exists, even with modest raw volume.

07

Public value

For civic namespaces: local adoption, verified actors, useful services, interoperability and measurable public value.

This is a framework, not a ranking. A TLD should be judged against the job it is meant to do.

Methodological guardrails

  • “Geographic” is an ICANN application classification; “city TLD” is a narrower analytical classification used in this publication.
  • Application counts, unique-string counts, registry portfolios, RSP-managed TLDs and delegated-TLD counts are different metrics and are never blended.
  • The 2026 application layer is post-Reveal. Official aggregate metrics and preliminary contention data are preserved locally. The Explorer additionally loads the published Reveal Day string inventory as a clearly identified external enrichment; complete application-level APS fields are not claimed as locally vendored. Strings and contention sets may still change during the replacement period before String Confirmation Day.
  • “Zeitgeist” themes and the five-layer power model are analytical classifications and remain separate from official ICANN fields.
  • Economic metrics retain their original accounting basis and currency. Public revenue, company revenue, operating income, transaction value, auction price and application fees are never treated as one comparable measure.
  • Social significance is not inferred from registration volume. Registry charters, eligibility rules and documented community policies are FACT; the broader meaning assigned to them in this publication is a READING.
